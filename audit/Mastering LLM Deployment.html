It fails with friends: data, product, security, ops, and budget. These six failure modes account for the overwhelming majority of pilot deaths.
Unclear use case
Built because it was possible, not because it solved a measurable problem.
Poor data
Sources are wrong, stale, permissioned, or unstructured beyond recovery.
No integration
The pilot ran in isolation. Production needs identity, data, and workflows.
No evaluations

No ownership
Built by a project team. Production needs a 24/7 owner with a paged rotation.

SLIDE S011
Discriminative vs.
Generative AI
LLMs behave fundamentally differently from traditional classifiers. The unit of decision changes.
CORE

What is this?
vs. what comes next?

Classifiers draw boundaries between known answers. Generators sample from a probability distribution over what to produce.
DISCRIMINATIVE · CLASSIFY
Question
"Which label fits this input?"
Output
One of a fixed set of answers
Confidence
A probability per class
Evaluation
Accuracy, F1, ROC — well-understood
Examples
Spam · sentiment · fraud · churn
GENERATIVE · PRODUCE
Question
"What is the most plausible next thing?"
Output
An open-ended sequence — text, code, JSON
Confidence
Per-token probability — easy to misread
Evaluation
Hard. Faithfulness, helpfulness, format
Examples
Chat · summarize · extract · code · agent

SLIDE S012
Why Generative
Is Harder
Generation changes the shape of every operational concern — latency, memory, evaluation, safety.
CORE

One prompt in.
Thousands of tokens out.

Autoregressive decoding flips the cost profile, the latency profile, and the safety profile of every request.
Autoregressive decoding
One token at a time, sequentially. Cost is per output token — not per request.
Variable-length output
You don't know when generation stops. Budget overruns become real.
Context window pressure
Long conversations and RAG silently degrade as context fills.
Hallucination risk
The model can be fluent and wrong. Confidence cues are misleading.
Sampling stochasticity
Same prompt, different output. Reproducibility is harder.
Output constraints
JSON, schema, length, safety — enforced post-hoc or via constrained decoding.

SLIDE S013
The Probability
Engine
An LLM is a next-token probability engine wrapped in product behavior. Quantization compresses step 03; caching reuses it. Sampling lives at step 04. Batching coordinates many parallel loops.
BACKUP

Magic on the surface.
A loop underneath.

Five stages, repeated for every output token. Every optimization technique we will see acts on one of these stages.
01 · INPUT
Text
The prompt — instructions, history, retrieved context.
02 · ENCODE
Tokens
Tokenizer splits text into subword IDs.
03 · COMPUTE
Logits
Model produces a distribution over the vocabulary.
04 · SAMPLE
Pick
Temperature, top-p, top-k select the next token.
05 · OUTPUT
Append
Append & repeat — until stop or budget.

SLIDE S040
BPE &
Subword Tokenization
Tokenizers split text into frequent subword pieces, not words. This is why "Deployment" is two tokens but "the" is one.
CORE

Subword pieces,
not whole words.

Byte-Pair Encoding (BPE) and its descendants build the vocabulary from frequent character pairs. Rare words decompose into common pieces; common words stay whole.
Vocabulary
Typically 32k–128k pieces. Larger vocab = fewer tokens per word, more parameters.

Special tokens
<|im_start|>, <|endoftext|>, role markers, function-call markers.
Implication for cost
Rare jargon, code, non-English text → more tokens → higher per-call cost.
Implication for context
A 32k context limit in tokens ≠ 32k words. Always measure with the target tokenizer.

Attention lets every token condition on every other token. Stack many of these layers and you get a language model.

[n_tokens, hidden_dim]

Each token computes weighted view of all previous tokens.

O(n²) in sequence length

A feed-forward network reshapes the token's representation.

~⅔ of model weights
STAGE 04
Repeat
Stack 30–100 of these blocks. Project final vector → vocab distribution.
OUTPUT
[vocab_size] logits → next token

SLIDE S050
The
KV Cache
Generation gets expensive because previous key/value states must stay available. Longer context, more users, more memory.
CORE

The model has
short-term memory.

For each new token, the model needs the attention states of every previous token. That memory is the KV cache — and it grows linearly with context and concurrent users.
What it stores
The key & value tensors for every past token, at every transformer layer.
Why it exists
Without it, generating each new token would recompute attention over all history.
How it grows
Linear in context length. Linear in concurrent requests. Quadratic in pain.
Why it hurts production
VRAM fragmentation. Each request holds a contiguous slab — even when half-empty.
The vLLM insight
PagedAttention — manage KV cache in fixed pages, like virtual memory. We will return to this.
What you can do
Cap max output. Trim history. Use prefix caching. Choose smaller cache footprints.

SLIDE S069
Why
Quantization Works
LLM weights are robust to some precision reduction. Weight distributions are concentrated; outliers get special handling.
BACKUP

Weights have a shape.
Use it.

Quantization is not "round each number." It is a measured scheme that preserves the dynamic range where weights actually live.
Distribution is narrow
Most weight values cluster near zero. A small int range covers the bulk.
Outliers matter
A few activations are huge. Modern quant schemes treat them specially.
Per-channel scaling
Each weight column gets its own scale factor. Better than one global scale.
Per-group quantization
Smaller groups → more accurate, slightly more overhead.
Symmetric vs. asymmetric
Symmetric is simpler & faster. Asymmetric fits skewed distributions.
Why not always quantize
Dequant overhead, kernel availability, and a small quality cost on some tasks.

FlashAttention
FlashAttention is a lossless attention optimization, not weight compression. Take it for free wherever your engine supports it.
DEEP DIVE

A free win.
Lossless. Take it.

FlashAttention rearranges the attention computation to minimize memory reads & writes. Same math, much faster — especially for long context.
The insight
Standard attention writes intermediate matrices to GPU memory. FlashAttention keeps them in fast SRAM.
The benefit
2–4× faster attention. Lower memory. No quality cost. Same math.
FlashAttention-2
Improved tiling & parallelism. Default in modern serving engines.
FlashAttention-3
Hopper-specific (H100) · uses FP8 paths and async TMA. Cutting edge.

vLLM · TGI · most transformers ≥ 4.40 · enabled by default in many model loads.

Modern Sparsity:
Mixture of Experts
Mixture of Experts is the practical sparsity story for LLMs — fewer active params per token, more total params. Faster active compute, larger memory footprint.
CORE

Many experts.
Few active per token.

MoE routes each token to a small subset of experts. You get the capability of a large model at the active-compute cost of a small one — at the price of holding all the experts in memory.
The idea
Replace one big feed-forward with N specialists. A router picks ~2 per token.
Examples
Mixtral · DeepSeek-V3 · Qwen3 MoE · GLM 4.x MoE.
Active vs. total params
Mixtral 8×22B has ~140B total but only ~39B active per token.
Throughput win
Active-FLOPs are a fraction of total — fast decoding for the capability.
Memory cost
All experts must be resident for the router to choose. Memory ≈ total params.
When it fits
You have memory headroom and you need frontier-class quality without frontier-class FLOPs.

LoRA
Mechanics
LoRA learns a low-rank update to selected weight matrices. Same effect as full fine-tuning at a fraction of the parameters.
CORE

W + B·A.

Instead of updating W directly, LoRA learns two small matrices whose product is the update. Inference adds them; storage stays small.

No — each request owns its slab

< 5% (last-page fragmentation only)

No evals
Ship & pray. Find out from users; lose trust; can't rollback safely.
